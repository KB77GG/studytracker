## 发现的缺陷：缓存在别的学生答题时存不住

现象（`cache-under-writes.json`，读者积压 2400 词，其他学生每人每 3 秒答一道复习题）：

| 同时答题的其他学生 | 紧接着的第二次读取命中缓存 |
| --- | --- |
| 0 | 12 / 12 |
| 1 | 9 / 12 |
| 3 | 7 / 12 |
| 6 | **0 / 12** |

原因有两层：
- 复习作答里的状态抢占用的是批量 `UPDATE vocabulary_review_item ... WHERE student_id = ?`。缓存模块对学生表的批量语句一律按"影响所有人"处理，于是**任何学生每答一题，所有学生的缓存都被清空**。
- 缓存发布用的是全局版本号：加载期间只要有任何写入（哪怕是别人的），刚算好的结果就不发布。

影响：只涉及显示数字的缓存，**不会显示错误数据**，门禁和选题也不受影响。损失的是性能——越是多人同时在线，缓存越不起作用，首页复习数和任务页门禁又回到每次约 0.75 秒的全量计算。Codex 报告里"随后缓存统计约 1–2 毫秒"是在没有其他写入的只读回放里测的。

### 补丁：`proposed-fix-cache-per-student-invalidation.patch`（未应用、未部署）

- 版本号拆成"全局（词库变更）+ 每学生"，别人的写入不再阻止本人结果发布；
- 批量语句可用执行选项声明它只涉及哪些学生，复习作答那一处已声明；没有声明的学生表批量语句仍按影响所有人处理，词库表写入仍清空所有人。

## 对我此前结论的更正

Codex 的规则审计指出我 11-16 报告里两处推断站不住，我核对后同意：
- "每做一个任务积压净增约 35–39 词"是用当前到期数除以任务数得到的截面比值，不是观测到的净增量，应撤回。
- "每批 20 词所以永远清不完"说过头了：20 是每批上限，不是每天上限。

仍然成立、且直接来自代码常量的是：阅读目标下每个词有 2 个维度，每个维度要按 1/3/7/14/30/60 天间隔答对 6 次才到最高阶段，之后仍每 60 天到期一次、没有退出；所以每学 40 个新词，头四个月内会排出约 480 次复习作答。而两个生产样本里每个任务对应的复习作答约 20 次。排期需求与实际完成量差一个数量级，这是规则层面的不匹配，但它是"按现有使用习惯做不完"，不是"原理上做不完"。
